You are not being asked to produce a generic app around a prompt. Choose one Entire innovation track
Your team must select one track. The project should solve a real developer or agent-workflow problem and make Entire essential to the solution. Adding Entire only for tracking, without using its context, checkpoints or graph evidence to improve the product, will not qualify.
Track 1 — Build a Checkpoint-Native Developer Experience
Build a developer tool or workflow powered by context preserved in Entire Checkpoints. Git shows what changed; checkpoints should preserve why a change happened, what the agent attempted, which assumptions were made, what failed and what remains unresolved.
Review an implementation against its stated intent.
Identify unfinished requirements or unresolved risks.
Create a change-risk or release-readiness report.
Hand work to another developer or agent without losing the original reasoning.
Resume an agent-assisted workflow with confidence after a break.
Success looks like this: checkpoint context is an essential input, and a developer or agent completes a useful task more accurately or efficiently than they could from a Git diff alone.
Track 2 — Build with Graph Intelligence
Use the Entire Graph’s structural view of a codebase to support a useful decision or action. The graph can surface definitions, call relationships, types, routes and semantic changes. Your product must turn that evidence into a workflow that a developer or agent can inspect and verify.
Impact-aware code review or change-risk analysis.
Test selection based on affected relationships.
Migration planning or dependency-aware refactoring.
Codebase onboarding and guided exploration.
Combining Entire Graph findings with checkpoint intent.
Raw graph output is not enough. Your product should produce a useful decision, recommendation or workflow, show where the evidence came from, and let the user verify it against source code or tests.
Track 3 — Bring Entire to a New Agent or Workflow
Extend or create an Entire integration for a coding agent, editor, development environment, CI process or software-delivery workflow. The integration must capture meaningful development context and keep working in its intended operating mode.
Support for a new coding agent or editor workflow.
A CI or pull-request workflow that uses checkpoint context.
A multi-agent coordination workflow.
A protocol adapter between Entire and another developer tool.
External SDKs and fixtures are allowed, but the submitted implementation must live in the designated Entire fork. Calling an Entire command from another interface is not sufficient by itself.

Required Entire workflow
Complete these steps after the 9:00 AM kickoff. All implementation must happen in the clone created through the Entire mirror workflow.
1. Fork your selected repository
Fork the repository associated with your chosen track only after the Buildathon begins. Use existing issues for inspiration, or propose an original feature, integration or workflow.
2. Sign in and create the mirror
entire login
entire repo mirror create
entire repo clone /gh/YOUR-GITHUB-HANDLE/REPOSITORY
Select your fork and the India region when prompted. Clone through Entire, then work inside that clone.
3. Enable checkpoints
entire enable -y --agent YOUR-BUILD-AGENT
entire status
Commit meaningful milestones so code and context remain connected. Your checkpoint history must include at least:
Initial understanding and intended architecture.
The last stable state before the Noon Curveball.
Your response to the Noon Curveball.
Final implementation and verification.
Checkpoint quality matters more than quantity. Capture decisions, rejected options, failures, assumptions, open risks and the evidence that changed your approach.
4. Activate Entire Graph
entire plugin install graph
entire graph version
entire graph init-agents --repo .
Start a fresh agent session after activation so the agent receives the graph instructions. During development, show at least:
A graph search or definition lookup.
A relationship or impact analysis before a high-risk change.
A final semantic diff analysis of the submitted implementation.
Graph results are evidence, not an oracle. Verify findings against source code, tests and runtime behavior. Never present incomplete or uncertain graph output as a fact.

The Noon Curveball
At exactly 12:00 noon, every team receives an additional track-specific constraint that becomes mandatory. The first version is the proof of what you built. The second version is the proof that your process can absorb change without losing intent.
11:45 AM — preserve the stable state
Stop adding optional features and get the product back to a runnable state.
Commit the last stable version.
Create the required pre-noon Entire Checkpoint.
Record the current intent, architecture, completed work, unresolved work and important technical risks.
12:00 PM — receive the constraint
Stop implementation and close the current coding-agent session.
Receive the official Curveball from the organising team. Do not exchange cards or use another track’s instruction.
Start a fresh agent session and use checkpoint context to reconstruct the project before editing.
Run Entire Graph impact analysis before changing the affected area.
Implement the smallest complete response, test it and record the result in a new checkpoint.
What judges will look for
A strong response preserves the product’s core idea, changes a real architectural or reliability decision, uses checkpoint context accurately, uses graph evidence where relevant, remains testable and explains why the revised behavior can be trusted.
The Curveball’s specific instructions are intentionally not published in advance. Mentors and organisers must not disclose them before noon.

⭐ Do you agree the moat is "did the agent do what it said," or do you think there's a sharper framing I'm missing?Why "did the agent do what it said" is the weaker framing
It checks a claim against a claim. The agent's self-report is the least trustworthy artifact in the room. If an agent is wrong about what it did, it's usually also wrong about what it said it would do. Building your headline on comparing those two makes your ground truth the same system you're auditing.

It requires an LLM, which kills claim #1. "I refactored auth and updated the tests" is natural language. Deterministically checking that against an entity-level diff isn't possible — you'd need a model to interpret intent. That directly contradicts "no LLM in the loop, same commit same verdict." And it invites the worst possible judge question at 2:50 PM: "so how do you compare the stated intent to the diff?" Either answer hurts you.

It's the obvious framing, which means several teams will arrive at it. It's also brittle: it does nothing when the agent said nothing, and nothing for human commits.

The sharper framing
It's already in your doc — you just haven't named it. Two sentences are doing the work:

"The graph says what structurally depends on the change; history says what habitually accompanies it."
"An empty selection is not evidence."

What those have in common: none of Gate's evidence comes from the agent. Blast radius comes from the code graph. Companion gaps come from the repo's own commit history. Coverage comes from the test tree. Not one input is the agent's description of its work.

An agent cannot make Gate say keep by describing its work well.

That's the moat, and I'd put that sentence in BUILDATHON.md. It's a one-liner, it's falsifiable on the spot, and it turns your determinism claim from a technical detail into the reason the tool can be trusted at all.

The second half is the absence framing: every other tool reports what it found. Gate reports what nobody looked at — where "nobody" means the agent, the developer, and the test suite. unchecked isn't a gap in your product; it's the product. That's why the trichotomy is your strongest idea and shouldn't be buried in §4.

Combined pitch:

Git shows what changed. Gate shows what that change put at risk and what nobody checked — using only evidence the agent didn't produce.

Two things this buys you that intent-checking doesn't: it works on human commits too (so "what happens when agents get better?" has an answer), and it's structural, not semantic — Gate supplies exactly the context an agent couldn't have had, because callers, co-change history, and coverage are invisible from inside the file being edited.

The practical point, given it's 10:30
This reframe requires zero code changes. Blast radius, companion gaps, and coverage are already agent-independent — you built the right thing and described it slightly wrong. It's a rewrite of the BUILDATHON.md opening and the pitch line, nothing more. That's why I'd take it: all upside, no build cost, on a day where build cost is everything.

What's worth keeping from the intent idea
One cheap, deterministic slice: if the Entire checkpoint records intended files or symbols in any structured form, diff that against what actually changed. That's a real "said vs did" check with no model involved. Ship it as a fourth finding type if you have slack after 2:15 — but don't put it in the pitch, and don't let it become the headline. It's a feature; the evidence-provenance argument is the moat.
